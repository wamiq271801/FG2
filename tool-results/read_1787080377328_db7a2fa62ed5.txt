     1→````markdown
     2→# Fusion Gadgets — Full Production System Implementation Plan
     3→
     4→## 1. Goal
     5→
     6→Convert the existing fully designed frontend from a mock/simulated store into a real production system without redesigning, simplifying, replacing, or degrading the existing premium UI.
     7→
     8→The current UI already exists. Preserve its visual quality, layout, motion, responsiveness, and premium feel. Replace the mock data layer and simulated actions behind it with real infrastructure.
     9→
    10→The final system has four main layers:
    11→
    12→```text
    13→NEXT.JS STOREFRONT
    14→        │
    15→        ├── Direct read access to Supabase
    16→        │
    17→        ├── Direct standard user-owned writes through RLS
    18→        │
    19→        └── Sensitive actions through Cloudflare Worker
    20→                    │
    21→                    ▼
    22→                 SUPABASE
    23→        Products / Users / Cart / Wishlist / Orders
    24→                    ▲
    25→                    │
    26→             Tracking output
    27→                    │
    28→          TRACKING PROCESSOR
    29→             Render Free
    30→                    ▲
    31→                    │
    32→                TiDB Cloud
    33→             Raw event storage
    34→                    ▲
    35→                    │
    36→          TRACKING INGEST API
    37→             Render Free
    38→                    ▲
    39→                    │
    40→                 Browser
    41→````
    42→
    43→The system must remain simple. Use built-in platform capabilities where they already solve the problem reliably.

    47→# 2. Core Architecture
    48→
    49→## Storefront
    50→
    51→Next.js App Router.
    52→
    53→The storefront is primarily static and server-rendered.
    54→
    55→Catalog and SEO pages use SSG and ISR.
    56→
    57→User-specific pages use static server-rendered shells. Only the interactive or user-data areas become Client Components.
    58→
    59→All important visible text must exist in the server-rendered HTML.
    60→
    61→Do not turn an entire page into a Client Component because one form, filter, button, or interactive section needs client code.
    62→
    63→The browser hydrates the required interactive components after the HTML is rendered.
    64→
    65→The frontend communicates directly with Supabase for normal reads and standard RLS-protected user-owned operations.
    66→
    67→The frontend communicates directly with the Cloudflare Worker only for sensitive actions that require server-side authority.
    68→
    69→The frontend communicates directly with the tracking ingest backend for batched tracking events.
    70→
    71→The frontend never communicates with TiDB.
    72→
    73→The frontend never communicates with the tracking processor.

   152→# 5. Home Page Data Flow
   153→
   154→The home page remains static/ISR.
   155→
   156→The tracking processor prepares compact circulation results in Supabase.
   157→
   158→The home page consumes the latest published ready data.
   159→
   160→```text
   161→TRACKING PROCESSOR
   162→        │
   163→        ▼
   164→SUPABASE READY RESULTS
   165→        │
   166→        ▼
   167→NEXT.JS ISR
   168→        │
   169→        ├── Read current products
   170→        ├── Read offers
   171→        ├── Read categories
   172→        └── Read published circulation results
   173→                │
   174→                ▼
   175→          Render complete HTML
   176→```
   177→
   178→Circulation results contain selection and ordering information, not duplicate product records.
   179→
   180→Next.js combines:
   181→
   182→```text
   183→READY PRODUCT ORDER
   184→+
   185→CURRENT PRODUCT DATA
   186→+
   187→CURRENT OFFER DATA
   188→=
   189→HOME PAGE
   190→```
   191→
   192→Validate that a circulated product is still active and eligible before rendering it.
   193→
   194→Do not recalculate circulation inside Next.js.
   195→
   196→Do not wait for tracking processing.
   197→
   198→If a section has no valid data, do not render that section.
   199→
   200→If circulation data does not yet exist, use a simple stable catalog fallback so the website still works.
   201→
   202→Do not recreate the circulation algorithm as a fallback.
   203→
   204→The last successful published result remains usable if processing fails.

   264→# 7. Product Data and Listings
   265→
   266→Products are read-only to normal users.
   267→
   268→Production listings must not be directly modifiable by browsers.
   269→
   270→Product creation and administration belong to the separate future admin system.
   271→
   272→The storefront only receives the public product data it is allowed to read.
   273→
   274→The public client must never receive a service-role key or other privileged database secret.
   275→
   276→Use Supabase's built-in access controls and database capabilities instead of inventing a custom product authorization system.
   277→
   278→A product must not become permanently hidden merely because it receives less engagement.
   279→
   280→The circulation system controls exposure and rotation, not permanent product suppression.
   281→
   282→New products must receive discovery opportunities.
   283→
   284→Older products must remain eligible when they are active and relevant.

   288→# 8. Offers

   290→Offers are stored as real database data.
   291→
   292→The development database must receive seed offers for testing.
   293→
   294→The storefront reads active offers and renders them using the existing UI.
   295→
   296→Offers are validated again during order creation.
   297→
   298→The browser display is never authoritative.
   299→
   300→The offer creation flow belongs to the future admin system, not the storefront Worker.

   303→
   304→Do not implement payment infrastructure while implementing offers.

   308→# 9. Authentication
   309→
   310→Supabase Auth is the authentication authority.
   311→
   312→The Worker is only a thin protection gate for selected abuse-prone entry points.
   313→
   314→The Worker does not own authentication state.
   315→
   316→The Worker does not own OTP state.
   317→
   318→The Worker does not create custom JWTs.
   319→
   320→The Worker does not manage token refresh.
   321→
   322→The Worker does not wait for users.
   323→
   324→The full authentication flow is:
   325→
   326→```text
   327→USER SUBMITS REGISTRATION
   328→        │
   329→        ▼
   330→CLOUDFLARE WORKER
   331→        │
   332→        ├── Validate request
   333→        ├── Rate limit
   334→        ├── Lightweight abuse checks
   335→        └── Call Supabase Auth
   336→                │
   337→                ▼
   338→             RETURN
   339→
   340→USER MAY TAKE MINUTES
   341→TO COMPLETE VERIFICATION
   342→        │
   343→        ▼
   344→BROWSER ↔ SUPABASE AUTH
   345→        │
   346→        ▼
   347→SESSION ESTABLISHED
   348→        │
   349→        ▼
   350→ONBOARDING
   351→        │
   352→        ▼
   353→SUPABASE + RLS
   354→        │
   355→        ▼
   356→ONBOARDING COMPLETE
   357→```
   358→
   359→Each request is independent.
   360→
   361→The Worker must return after completing the registration request.
   362→
   363→It must never wait for OTP entry.
   364→
   365→It must never hold an onboarding session open.
   366→
   367→OTP verification uses Supabase Auth.
   368→
   369→Session persistence and token refresh use the Supabase SDK.
   370→
   371→The application uses authentication state changes to handle sign-in and sign-out.
   372→
   373→When an authenticated session becomes invalid, clear private account-scoped client state and redirect to the sign-in flow.
   374→

   377→# 10. Registration and Onboarding
   378→
   379→Phone information required by the business onboarding flow must be completed before onboarding is considered complete.
   380→
   381→Address is optional during onboarding.
   382→
   383→Address becomes mandatory during checkout.
   384→
   385→The onboarding state is persisted in the user's real profile data.
   386→
   387→If the user leaves onboarding:
   388→
   389→```text
   390→ACCOUNT EXISTS
   391→        │
   392→        ▼
   393→ONBOARDING INCOMPLETE
   394→        │
   395→        ▼
   396→USER RETURNS LATER
   397→        │
   398→        ▼
   399→SIGN IN
   400→        │
   401→        ▼
   402→READ ONBOARDING STATE
   403→        │
   404→        ├── Complete → continue normally
   405→        │
   406→        └── Incomplete → resume onboarding
   407→```
   408→
   409→Do not keep onboarding progress in Worker memory.
   410→
   411→Do not keep a Worker request open while the user completes onboarding.
   412→
   413→Do not autosave every keystroke.
   414→
   415→Persist meaningful completed steps or explicit saves only.

   487→```text
   488→Profile
   489→Addresses
   490→Cart
   491→Wishlist
   492→```

   494→RLS must enforce ownership.
   495→
   496→```text
   497→USER
   498→        │
   499→        ▼
   500→SUPABASE REQUEST
   501→        │
   502→        ▼
   503→JWT
   504→        │
   505→        ▼
   506→RLS
   507→        │
   508→        ├── Own data → allow
   509→        │
   510→        └── Other user's data → deny

   517→# 14. Account Isolation and Client Cache
   518→
   519→Each authenticated account must remain isolated.
   520→
   521→Account-specific browser data must be scoped to the authenticated user.
   522→
   523→The flow is:
   524→
   525→```text
   526→USER A DATA
   527→        │
   528→        ▼
   529→SIGN OUT
   530→        │
   531→        ▼
   532→CLEAR PRIVATE CACHE
   533→        │
   534→        ▼
   535→USER B SIGNS IN
   536→        │
   537→        ▼
   538→LOAD USER B DATA
   539→```
   540→
   541→User A data must never appear under User B.
   542→
   543→The same applies to cart, wishlist, profile data, addresses, and cached queries.
   544→
   545→Do not use one anonymous global cache for authenticated account data.

   550→
   551→Cart items belong to the authenticated user and sync through Supabase with RLS.
   552→
   553→Guest cart data may exist locally before sign-in.
   554→
   555→After authentication:
   556→
   557→```text
   558→GUEST CART
   559→+
   560→ACCOUNT CART
   561→        │
   562→        ▼
   563→MERGE
   564→        │
   565→        ▼
   566→SUPABASE ACCOUNT CART
   567→        │
   568→        ▼
   569→SUCCESS
   570→        │
   571→        ▼
   572→CLEAR GUEST CART
   573→```
   574→
   575→Do not destroy guest cart data before the merge succeeds.
   576→
   577→Do not overwrite account cart blindly.
   578→
   579→The merge must preserve the intended items according to the real product rules.
   580→
   581→After sign-out, private account cart cache must be cleared.

   618→
   619→```text

   622→        ▼
   623→CHECKOUT

   625→        ├── Load current cart
   626→        ├── Select or create address
   627→        └── Review order
   628→                │
   629→                ▼

   646→# 18. Order Creation
   647→
   648→Order creation always goes through the Cloudflare Worker.
   649→
   650→The browser does not send a trusted total.
   651→
   652→The browser does not send trusted prices.
   653→
   654→The browser does not decide whether an offer is valid.
   655→
   656→The Worker performs the authoritative checkout operation.
   657→
   658→```text
   659→PLACE ORDER
   660→        │
   661→        ▼
   662→WORKER
   663→        │
   664→        ├── Authenticate request
   665→        ├── Validate request
   666→        ├── Rate/abuse checks
   667→        ├── Idempotency check
   668→        ├── Read authoritative cart
   669→        ├── Verify selected address ownership
   670→        ├── Verify products
   671→        ├── Verify availability
   672→        ├── Recalculate prices
   673→        ├── Revalidate offers
   674→        └── Calculate final total
   675→                │
   676→                ▼
   677→        ATOMIC ORDER CREATION
   678→                │
   679→                ├── Create order
   680→                ├── Create order items
   681→                ├── Snapshot prices
   682→                ├── Snapshot product details required for history
   683→                ├── Snapshot delivery address
   684→                └── Update purchased cart state
   685→                        │
   686→                        ▼
   687→                    SUCCESS
   688→```
   689→
   690→Clear local cart state only after confirmed success.
   691→
   692→Use idempotency to prevent duplicate orders caused by retries, double-clicks, or uncertain network responses.
   693→
   694→A repeated successful request with the same checkout idempotency key must return the existing successful result rather than create another order.
   695→
   696→The Worker must perform only the required work and complete the request efficiently.
   697→
   698→Do not turn order creation into a multi-request workflow.
   699→

   701→
   702→# 19. Order and Address Snapshots
   703→
   704→Orders must preserve historical truth.
   705→
   706→The delivery address is copied into the order when the order is created.
   707→
   708→Later editing or deleting the user's saved address must not change historical orders.
   709→
   710→Product and price information required to represent the historical order is also snapshotted.
   711→
   712→Do not rebuild old order totals from current product prices.
   713→
   714→Do not make old orders depend on the current product record remaining unchanged.
   715→

   765→The Cloudflare Worker is not a general backend proxy.
   766→
   767→It exists for sensitive short-lived operations.
   768→
   769→Primary responsibilities:
   770→
   771→```text

   773→Password reset request protection
   774→Order creation
   775→Other future sensitive operations only when necessary
   776→```
   777→
   778→Every Worker request follows:
   779→
   780→```text
   781→REQUEST
   782→        │
   783→        ▼
   784→VALIDATE
   785→        │
   786→        ▼
   787→RATE LIMIT / REQUIRED SECURITY CHECK
   788→        │
   789→        ▼
   790→PERFORM REQUIRED ACTION
   791→        │
   792→        ▼
   793→RETURN
   794→```
   795→
   796→The Worker must not wait for user actions.
   797→
   798→The Worker must not run background processing.
   799→
   800→The Worker must not process tracking events.
   801→
   802→The Worker must not perform admin actions.
   803→
   804→The Worker must not sit between Next.js and Supabase during SSG or ISR.
   805→
   806→The Worker must not proxy normal catalog reads.
   807→
   808→The Worker must not proxy normal profile, cart, wishlist, or address operations.
   809→
   810→Do not add Next.js API routes as an unnecessary extra backend layer.

   860→# 24. Frontend Event Collection
   861→
   862→Do not send one request per event.
   863→
   864→Events enter a bounded browser queue.
   865→
   866→The queue batches events and sends them efficiently.
   867→
   868→Each event has a unique event ID.
   869→
   870→If delivery fails:
   871→
   872→```text
   873→KEEP EVENT
   874→        │
   875→        ▼
   876→RETRY LATER
   877→```
   878→
   879→Use controlled retry behavior.
   880→
   881→Do not retry forever.
   882→
   883→Do not allow unlimited browser storage.
   884→
   885→Do not block navigation waiting for analytics.
   886→
   887→Low-value events may be discarded when the bounded queue reaches its limit.
   888→
   889→The tracking endpoint must remain lightweight.
   890→

   893→# 25. Tracking Ingest Backend
   894→
   895→Host the tracking ingest API on Render.
   896→
   897→Its responsibility is only:
   898→
   899→```text
   900→Receive batch
   901→Validate batch
   902→Deduplicate
   903→Bulk insert into TiDB
   904→Return
   905→```
   906→
   907→It does not calculate metrics.
   908→
   909→It does not calculate circulation.
   910→
   911→It does not write raw events to Supabase.
   912→
   913→It remains stateless.
   914→
   915→Use efficient asynchronous request handling and bounded database concurrency.
   916→
   917→Do not add Redis, Kafka, RabbitMQ, or another queue.
   918→
   919→Do not create a persistent in-memory event queue.
   920→

   922→
   923→# 26. TiDB Event Storage
   924→
   925→TiDB stores raw tracking events.
   926→
   927→Events are append-oriented and indexed for incremental processing.
   928→
   929→Each event has:
   930→
   931→```text
   932→Internal ordered event key
   933→Unique event ID
   934→Event type
   935→Occurred time
   936→Received time
   937→Relevant product/category identifiers
   938→Minimal user/session context when required
   939→```
   940→
   941→Store only data required for analytics and circulation.
   942→
   943→Do not store unnecessary PII.
   944→
   945→Do not store huge browser payloads.
   946→
   947→Do not store complete request headers.
   948→
   949→Do not store redundant data repeatedly.
   950→
   951→Raw events must have a retention strategy so the event store does not grow forever.
   952→

   954→
   955→# 27. Incremental Tracking Processor
   956→
   957→Host the processor separately on Render.
   958→
   959→Cron wakes it when processing is required.
   960→
   961→The processor never scans the full event history repeatedly.
   962→
   963→Use a persistent checkpoint.
   964→
   965→```text
   966→CHECKPOINT
   967→        │
   968→        ▼
   969→READ ONLY EVENTS AFTER CHECKPOINT
   970→        │
   971→        ▼
   972→PROCESS BATCH
   973→        │
   974→        ▼
   975→WRITE RESULTS
   976→        │
   977→        ▼
   978→ADVANCE CHECKPOINT
   979→        │
   980→        ▼
   981→REPEAT UNTIL CAUGHT UP
   982→```
   983→
   984→The checkpoint advances only after the corresponding processing work succeeds.
   985→
   986→Never advance the checkpoint before results are safely persisted.
   987→
   988→Do not load all unprocessed events into memory.
   989→
   990→Process bounded batches.
   991→
   992→The processor must use a persistent lock to prevent overlapping cron runs from processing the same work.
   993→
   994→If another processor run already owns the lock, exit safely.
   995→
   996→The lock must recover after crashes.
   997→
   998→Do not rely on Render local storage for locks or checkpoints.
   999→

  1001→
  1002→# 28. Tracking Processing Output
  1003→
  1004→The processor turns raw events into compact useful data.
  1005→
  1006→The processor owns the circulation decisions.
  1007→
  1008→Next.js does not recalculate scores.
  1009→
  1010→The processor produces:
  1011→
  1012→```text
  1013→Compact product metrics
  1014→Ready circulation results
  1015→Prepared product ordering for surfaces
  1016→```
  1017→
  1018→Supabase stores only the ready-to-consume output needed by the storefront.
  1019→
  1020→Do not copy the entire raw event history into Supabase.
  1021→
  1022→The processor may aggregate multiple event types into compact product-level metrics.
  1023→

  1026→# 29. Published Result Safety
  1027→
  1028→Never expose half-written circulation results.
  1029→
  1030→The flow is:
  1031→
  1032→```text
  1033→CURRENT PUBLISHED VERSION
  1034→        │
  1035→        ▼
  1036→PROCESSOR BUILDS NEW VERSION
  1037→        │
  1038→        ▼
  1039→WRITE COMPLETE NEW RESULT SET
  1040→        │
  1041→        ▼
  1042→SUCCESS?
  1043→        │
  1044→        ├── NO → keep old published version
  1045→        │
  1046→        └── YES → publish new version
  1047→```
  1048→
  1049→Next.js reads only a complete published version.
  1050→
  1051→If processing fails, the last good result remains available.
