# 1. Phase 7 Objective

Implement the tracking pipeline as a completely separate system from the Cloudflare Worker.

The final architecture is:

```text
NEXT.JS FRONTEND
        │
        │ Batched tracking events
        ▼
TRACKING SERVER
        │
        │ Durable event storage
        ▼
TiDB Cloud
        │
        ▼
PROCESSING SERVER
        │
        │ Process only new/unprocessed work
        ▼
Ready-to-use aggregated data
        │
        ▼
Supabase
        │
        ▼
Next.js ISR / public reads
```

The critical rule is:

> **Tracking data is not processed synchronously by the frontend, Next.js, Cloudflare Worker, or Supabase.**

The tracking system must be independent.

If tracking processing is unavailable:

```text
Tracking processing unavailable
        │
        ▼
Existing ready Supabase data remains available
        │
        ▼
Website continues working
```

The storefront must never depend on live tracking processing.

# 8. Processing Must Be Incremental

This is one of the most important requirements.

The ProcessingServer must never repeatedly process the entire event table.

Forbidden:

```text
SELECT all events
↓
recalculate everything
↓
write everything again
```

Instead:

```text
Events
  │
  ├── Already processed
  │
  └── New/unprocessed
          │
          ▼
     Process only these
```

The system must maintain a reliable checkpoint/watermark.

Use a simple mechanism such as:

```text
last_processed_event_id
```

or another monotonic processing cursor supported by the actual schema.

Do not use timestamps alone if they can cause missed events or duplicate windows.

If IDs are not monotonically usable, use a proper durable cursor strategy.

Keep it simple.

---

# 9. Processing Cursor

The processing checkpoint must itself be durable.

It must survive:

```text
Render restart
Deployment
Free-plan sleep
Crash
Processing failure
Manual restart
```

Do not keep the only checkpoint in memory.

The checkpoint must be stored in durable storage.

TiDB is the natural location for the event-processing checkpoint unless the actual architecture has a concrete reason otherwise.

The flow is:

```text
Read checkpoint
      ↓
Fetch events after checkpoint
      ↓
Process bounded batch
      ↓
Successfully persist derived state
      ↓
Advance checkpoint
```

Do not advance the checkpoint before the derived state is safely persisted.

---

# 10. Failure Safety

If processing fails halfway through:

```text
Processed successfully
        │
        ▼
Checkpoint advances only through confirmed work
```

Do not mark unprocessed events as processed.

Do not lose events because one event failed.

Do not advance the cursor to the end of a fetched batch before successful processing.

The system must be restartable.

At-least-once processing is acceptable.

The resulting aggregation must therefore be idempotent.

---

# 11. Idempotent Processing

Processing the same event twice must not corrupt aggregate data.

The system must tolerate:

```text
Render restart
Network retry
Cron overlap
Processing crash
Manual re-run
```

Do not assume exactly-once execution.

Use database constraints/upserts/checkpoints where appropriate.

Do not build a distributed transaction system.

Keep idempotency simple and database-backed.

---

# 12. Processing Concurrency

The ProcessingServer must avoid two cron invocations processing the same cursor simultaneously.

Use a simple distributed lock or database-backed processing lease.

The lock must:

```text
Prevent concurrent processors
Expire safely
Not remain permanently stuck after crash
Be inexpensive
```

Do not introduce Redis.

Do not introduce another database.

Do not build a custom distributed coordination service.

TiDB can provide the necessary durable coordination if implemented correctly.

If the Render instance itself guarantees single execution for the deployment, still protect the processing endpoint against overlapping external cron calls.

---

# 13. Bounded Processing

Each ProcessingServer invocation must process a bounded amount of work.

For example:

```text
Trigger
   ↓
Acquire lock
   ↓
Read up to N events
   ↓
Process
   ↓
Persist
   ↓
Advance checkpoint
   ↓
If more work remains, process another bounded batch only within a safe execution limit
   ↓
Release lock
   ↓
Return
```

Do not create an infinite loop.

Do not let a single cron request run indefinitely.

Use a practical execution budget compatible with Render free-tier behavior.

If work remains, the next cron invocation can continue.

Correctness is more important than processing the entire backlog in one request.

---


Supabase receives only the data the storefront actually needs.

This keeps Supabase small and useful.
